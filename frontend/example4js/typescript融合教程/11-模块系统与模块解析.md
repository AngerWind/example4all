# 模块系统与模块解析

## 1. 模块和脚本

在 TypeScript 中，一个文件如果包含顶层 `import` 或 `export`，它就是模块；否则通常会被当作脚本文件，顶层声明可能进入全局作用域。

```ts
export const name = "module";
```

如果一个文件没有实际导入导出，但你希望它被当成模块，可以写：

```ts
export {};
```

这在写全局类型扩展时很常见。

## 2. ES Module 导出

命名导出：

```ts
export const count = 1;

export function add(a: number, b: number) {
  return a + b;
}
```

统一导出：

```ts
const a = 1;
const b = 2;

export { a, b };
```

默认导出：

```ts
export default function createUser() {
  return { name: "jack" };
}
```

重导出：

```ts
export * from "./utils";
export { add } from "./math";
export { default as createUser } from "./user";
```

## 3. ES Module 导入

命名导入：

```ts
import { add } from "./math";
```

命名空间导入：

```ts
import * as math from "./math";
```

默认导入：

```ts
import createUser from "./user";
```

只导入类型：

```ts
import type { User } from "./types";
```

`import type` 明确告诉 TypeScript 该导入只用于类型位置，不应作为运行时代码保留。

## 4. CommonJS

CommonJS 常见于 Node.js 旧项目：

```js
const fs = require("fs");

function add(a, b) {
  return a + b;
}

module.exports = {
  add
};
```

注意正确名称是 `module.exports`，不是 `module.export`。

TypeScript 中可以这样写：

```ts
import fs = require("fs");
```

或者在启用相关互操作配置后：

```ts
import fs from "fs";
```

这取决于 `module`、`moduleResolution`、`esModuleInterop`、运行时和构建工具配置。

## 5. ESM 和 CommonJS 的关键区别

ES Module：

- 静态结构，`import` / `export` 必须在顶层。
- 更适合 tree shaking。
- 导入绑定是只读的 live binding。
- 在 Node.js 中受 `package.json` 的 `"type": "module"`、文件扩展名、`exports` 等影响。

CommonJS：

- `require` 是运行时调用，可以放在条件语句里。
- 导出值通过 `module.exports`。
- Node.js 传统生态中大量存在。

教程中“ESM 导入 CommonJS 很方便”的描述要加前提：真实行为取决于 Node.js 版本、`esModuleInterop`、`allowSyntheticDefaultImports`、打包工具和库的导出形式。

## 6. package.json 常见字段

`main`：CommonJS 或传统 Node 入口常用字段。

```json
{
  "main": "dist/index.cjs"
}
```

`module`：很多打包工具使用的 ESM 入口字段；Node.js 原生并不把它作为标准入口。

```json
{
  "module": "dist/index.mjs"
}
```

`types` / `typings`：TypeScript 类型声明入口。

```json
{
  "types": "dist/index.d.ts"
}
```

`type`：控制 `.js` 文件按 ESM 还是 CommonJS 解释。

```json
{
  "type": "module"
}
```

`exports`：现代包的导出入口和子路径控制。

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./style": "./dist/style.css"
  }
}
```

如果配置了 `exports`，未暴露的内部路径通常不能被外部导入。

## 7. TypeScript 的模块解析

`moduleResolution` 决定 TypeScript 如何根据导入路径查找文件和类型声明。

早期教程常提 `classic` 和 `node`：

```json
{
  "compilerOptions": {
    "moduleResolution": "node"
  }
}
```

现代项目更常见：

```json
{
  "compilerOptions": {
    "moduleResolution": "node16"
  }
}
```

或：

```json
{
  "compilerOptions": {
    "moduleResolution": "bundler"
  }
}
```

大致选择：

- Node.js ESM/CJS 项目：`node16` 或 `nodenext`。
- Vite、Webpack、Rollup 等打包项目：通常用 `bundler` 或框架模板默认配置。
- 老项目：可能仍使用 `node`。

## 8. 相对导入解析

```ts
import { b } from "./moduleB";
```

TypeScript 会根据配置查找可能的文件，例如：

```text
./moduleB.ts
./moduleB.tsx
./moduleB.d.ts
./moduleB/package.json
./moduleB/index.ts
./moduleB/index.d.ts
```

在 Node ESM 模式下，相对导入的扩展名规则更严格，运行时代码可能需要写 `.js` 扩展名：

```ts
import { b } from "./moduleB.js";
```

这点是老教程里经常没讲全的地方。

## 9. 非相对导入解析

```ts
import axios from "axios";
```

TypeScript 会向上查找 `node_modules`，并读取包的 `package.json`、`types`、`exports`、`@types` 等信息。

如果库没有类型，可能会看到类似错误：

```text
Could not find a declaration file for module 'xxx'
```

解决方式：

```bash
npm install -D @types/xxx
```

如果没有现成类型，就自己写 `declare module "xxx"`。

## 10. 路径别名

TypeScript 中可用 `baseUrl` 和 `paths`：

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

然后：

```ts
import { add } from "@/utils/add";
```

注意：`paths` 只影响 TypeScript 类型检查和编译解析，不一定自动影响运行时。运行时或打包工具也要配置对应别名。

## 11. npm link 和本地包

教程里提到 `npm link`，它可以把本地包链接到另一个项目：

```bash
cd ../hello
npm link

cd ../app
npm link hello
```

适合本地调试包，但要注意：

- 可能引入依赖重复问题，尤其是 React 这类单例依赖。
- ESM/CJS 入口、`types`、`exports` 要配置一致。
- 发布前仍应验证正常 `npm install` 的行为。

更现代的本地开发也常用 workspace：

```json
{
  "workspaces": ["packages/*", "apps/*"]
}
```
